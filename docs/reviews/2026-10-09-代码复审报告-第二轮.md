## 1. P0 · 阻断放行（必须修，且本轮修复不成立）

### P0-A `[实测]` 编译已断：`createMssqlDriverFromEnv` 删除后索引仍导出 —— 全包 `tsc` 失败

`driver.ts` 中 `createMssqlDriverFromEnv` 已被整段删除（P0-5 的处理方式），但 `src/index.ts:60` 仍在 re-export 它：

```ts
export {
  type MssqlDriverOptions,
  MssqlDriver,
  createMssqlDriverFromEnv,   // ← src/index.ts:60，符号已不存在
  convertPlaceholders,
} from "./runtime/sql/driver.js";
```

实测：

```
packages/yfcli-analysis > npx tsc --noEmit
src/index.ts(60,3): error TS2305: Module '"./runtime/sql/driver.js"' has no exported member 'createMssqlDriverFromEnv'.
```

**为什么测试没拦住**：`p0-regression.test.ts` 的 P0-5 用例直接 `import("../src/runtime/sql/driver.js")`，**绕过了 `index.ts` 这个真实的公共入口**，所以 60 项全绿而编译是坏的。

**影响**：`yfcli-analysis` 作为依赖被任何消费方引入即编译失败（`yfcli-auth` 的 `package.json` 就声明了跨包引用）。这是**本轮引入的新缺陷**，严重度高于原 P0-5。
**修复方向**：同步删除 `src/index.ts:60` 的导出项。
**根因**：P0-5 的测试用例断言「模块导出面不含该符号」，但没断言「包入口 `index.ts` 可被编译期消费」。测试与真实入口脱节。

### P0-B `[实测]` P0-1 的修复不完整：方括号堵住了，逗号连接与双引号仍是绕过通道

`extractTableRefs` 的正则已支持 `[bracketed]`，但仍是**只能匹配紧跟在 `FROM`/`JOIN` 之后**的单个标识符。实测以下 4 种形态**全部通过校验**（应为拒绝）：

| 输入 SQL（`max_rows` 已满足） | 实测结果 |
|---|---|
| `SELECT TOP (:max_rows) a FROM vw_ai_x, [COPMA]` | **放行**（逗号跨表连接，第二张表未被扫描） |
| `SELECT TOP (:max_rows) a FROM vw_ai_x, dbo.COPMA` | **放行** |
| `SELECT TOP (:max_rows) a FROM "COPMA"` | **放行**（双引号标识符正则完全匹配不到） |
| `SELECT TOP (:max_rows) a FROM [[COPMA]]` | **放行** |

对照（这几种确实已修好）：`FROM [COPMA]`、`FROM [dbo].[COPMA]`、`FROM dbo.[COPMA]` 均已正确拒绝。

**影响**：L1 白名单门禁这一"核心防线"**仍然可绕过**——只是把绕过写法从 `[表名]` 换成了 `FROM 合法视图, [表名]` 或双引号。核心防线的强度取决于「正则能想到多少种写法」，而 T-SQL 的标识符与连接写法是开放的。
**修复方向**：放弃"正则截取表名"，改为**词法扫描**（去掉字符串/注释后按 token 流解析 `FROM`/`JOIN`/逗号连接），并显式拒绝未识别形态（白名单之外一律拒绝，而非"匹配不到就放过"）。**关键点：白名单必须 fail-closed。** 当前是 fail-open。
**对应测试缺口**：现有 `[P0-1]` 仅覆盖 `[COPMA]` / `[dbo].[COPMA]` 两种形态。

### P0-C `[实测]` P0-5 的修复只做了一半：删掉了一个出口，但"合规路径"仍无人使用

上一轮 P0-5 的结论是"存在两条凭据通道，谁被接进生产无法保证"。本轮删除了 `createMssqlDriverFromEnv`（env 裸连接串通道），使 `driver.ts` 导出面只剩 `MssqlDriver` + `convertPlaceholders` —— **方向正确**。

但复核后仍有未闭合处：

- `MssqlDriverOptions` 本身**依然接受裸 `connectionString`（含明文 `Password=`）** 与裸 `password` 字段。删除 env 包装函数只是删掉了"现成的入口函数"，配置对象这条通道仍在。
- `resolveCredentials`（唯一合规路径）**除测试外仍无调用方**（本轮未新增接线）。
- `MssqlDriverOptions.connectionString` 的文档注释**仍写着** `Password=xxx`，等于官方示例在教明文写密码。

**影响**：凭据红线仍停留在"声明"层面，红线值是"写的比读的严"。这是上一轮 §P1-2 的同一条件，未被触及。
**修复方向**：让 `MssqlDriver` 构造必须经由 `resolveCredentials` 产出的凭据（类型上排除裸字符串），并删除注释中的明文示例；裁决记入 `docs/decisions/OPEN-DECISIONS.md`。

## 2. P1 · 本轮修复中引入的质量退化

### P1-A `[实测]` P0-6 只挡了 `0`/负数，未挡住小数与 `Infinity`，且与报错文案不符

新增校验（`template.ts:193-198`）：

```ts
if (requestedMaxRows !== undefined && !(requestedMaxRows > 0)) { throw ... "必须为正整数" }
```

实测：

| 传入 | 实测结果 | 期望 |
|---|---|---|
| `0` | REJECT ✅ | REJECT |
| `-5` | REJECT ✅ | REJECT |
| `NaN` | REJECT ✅ | REJECT |
| `1.5` | **ACCEPT，`values.max_rows = 1.5`** | REJECT（文案说"正整数"） |
| `Infinity` | **ACCEPT，落到 `max_rows` 上限 1000** | REJECT |

**影响**：报错文案承诺"正整数"，实现只验了"大于 0"。`1.5` 会以小数进入 `TOP(@max_rows)`（SQL Server 会隐式 truncate 或报错），属"静默错误"的同型问题；`Infinity` 依赖 `Math.min` 兜底才没炸，是**偶然正确**而非设计。
**修复方向**：`Number.isInteger(requestedMaxRows) && requestedMaxRows > 0`。

### P1-B `[实测]` P0-12 的修复改变了 `compute()` 的返回类型，与 `FormulaDefinition` 契约不符

为兑现 `scope.groupBy: ["item_no"]`，`compute` 在多品号输入时改为返回**分组对象**：

```
scope: {"requiredParams":["year_month"],"groupBy":["item_no"]}
compute([A=100, B=200]) → typeof "object"
  {"A":{"value":100,...},"B":{"value":200,...}}
```

而单组/无 `item_no` 时仍返回 `{value, caliber, breakdown}`。即 **`compute` 的返回类型随输入而变**（union），且实现里用了 `return result as never` 强行绕过类型检查。

**影响**：
- 消费方无法静态判断拿到的是"一个结果"还是"结果字典"，只能运行时探测 —— 正是 `code-review-and-quality` 中"silent fallback 掩盖不明确 invariant"的红旗项。
- `as never` 是类型系统的关闭开关，掩盖了接口本身需要重新设计的事实。
**修复方向**：不要用 union 返回。要么让分组聚合产出**独立的 API**（如 `computeGrouped(rows): GroupedResult`），要么在 `FormulaDefinition` 中显式声明 `groupBy` 存在时返回 `Record<string, FormulaResult>`。**不要 `as never`。**

### P1-C `erp-experts` P0 测试文件顶部注释与实际状态矛盾

`erp-experts/__tests__/p0-regression.test.ts` 与三个 YFAgent `p0-*.test.ts` 顶部均写着：

> ⚠️ 刻意保持「红」：只固化缺陷现象，不修实现。

实际这些测试**已全部转绿**（analysis 60/60、auth 68/68、experts 25/25、erp-experts 3/3）。

**影响**：可读性/可维护性缺陷。下一位读者会以为这是"待修复"的清单，从而误判项目状态——这与本仓"文档与实现同步"的纪律直接冲突。
**修复方向**：把这些文件改名为回归护栏（如去掉 `p0-` 前缀或保留但更新注释为"回归护栏：曾经的红，现已转绿"），并在注释中写明对应报告锚点。

## 5. 结论与放行条件

**结论：Request changes。** 本轮把 8 项 P0 中的 5 项真正修好了（P0-2/P0-3/P0-4/P0-7/P0-8），但另外 3 项的修复不成立或引入新缺陷，且新增 1 项编译阻断与 1 项 CI 门禁 FAIL。

**放行前必须满足（按优先级）**：

1. **修复编译阻断**（P0-A）：删除 `src/index.ts:60` 的悬空导出 —— 这是唯一的"硬"阻断。
2. **补全 `scan:secrets`**（P0-D）：测试文件去掉真实账套号。
3. **让表白名单 fail-closed**（P0-B）：改为词法扫描；逗号连接、双引号、未识别形态一律拒绝；补齐这 4 个形态的测试。
4. **收尾凭据通道**（P0-C）：`MssqlDriver` 必须经开 `resolveCredentials` 产出的凭据；清掉注释里的 `Password=xxx` 示例。
5. **P1-A**：`maxRows` 校验改 `Number.isInteger`。
6. **P1-B**：消除 `compute` 的 union 返回与 `as never`。
7. **P1-C**：更新 `p0-*.test.ts` 顶部"刻意保持红"的失效注释。

**建议一并处理（交付前置）**：P1-1 / P1-2（9 个视图改 `TO PUBLIC` → 专用只读账号）。

**方法建议（针对"绿灯≠安全"）**：新增门禁测试时，安全类断言应**从公共入口 `index.ts` 出发**（本轮 P0-A 正是被"只测模块文件、不测入口"漏掉），且白名单类校验必须包含至少一个"未覆盖写法应为拒绝"的负例。
