# 统计口径规范

> 生效日期：2026-10-08
> 起因：非标准列名计数历经 6 轮修订（4 → 24 → 684 → 761 → 722 → 711），
> 表级数字出现 9 个值（92 / 94 / 65 / 67 / 1141 / 1165 / 1168 / 1169 / 1171）。
> **根因不是算错，是跨口径相减与裸数字对比。**

---

## 一、强制规则

### 规则 1：任何统计量必须带口径标签

**禁止裸数字。** 出现数字时必须能回答「什么口径」。

| 标签 | 定义 | 用途 |
|---|---|---|
| `[严格]` | 剔除元数据表 + 剔除 UDF | 唯一有业务意义的口径，对外引用只准用这个 |
| `[含UDF]` | 剔除元数据表，UDF 计入 | 仅供与历史数据换算 |
| `[双来源并集]` | fields.json 并集 tables.json，剔除元数据表 | 解释「表清单与字段清单不一致」 |
| `[字段级]` / `[表级]` | 统计对象粒度 | 必须与口径标签组合使用 |

**正确写法**：

```
非标准列名 [严格][字段级] = 711
部分非标准表 [严格][表级] = 67
```

**错误写法**：

```
非标准列名 711 个        ← 未标口径，虽数值对但无法判断是否含 UDF
711 - 22 = 689          ← 数值恰好对（同为[严格]），但未标口径，读者无法确认
```

### 规则 2：禁止跨口径相减

所有减法必须同口径。**反例（本轮实际发生）**：

```
误例：含UDF 表数 1165− 全非标准表数 27 = 1138
      ^^^^^^^ [含UDF] 口径      ^^^^ [严格] 口径
      两者不同源，相减无意义
```

**正例（同口径合法）**：

```
      含>=1 非标准 1168 − 全非标准 27 = 1141
      ^^^^^^^^^^^^^^ 均为[含UDF] 剔元数据
      → 得到该口径下的「部分非标准表数 1141」
```

**关键区别**：同口径相减得到的是**该口径下的另一个指标**；跨口径相减得到的**不是任何指标**。

### 规则 3：断言值必须带口径前缀

```python
assert cnt_ns_field_strict == 711, "[严格][字段级] 非标准列名"
assert cnt_tbl_partial_strict == 67, "[严格][表级] 部分非标准表"
```

### 规则 4：表级统计必须声明两个变量

元数据有两处易被忽略的口径分歧，**叠加后产生全部偏差**：

| 变量 | 选项 | 默认 |
|---|---|---|
| 表集合基准 | `fields`侧 1170 / `tables`侧 1170 / 并集 1174 | `fields`侧 |
| 管理字段 | 保留 / 剔除 | **保留** |

缺任一声明，同一指标会有两个值。统计表级数字时必须写成：

```
部分非标准表 [fields侧][保留管理字段][不含UDF] = 67
```
### 规则 5：新发现的变体登记为独立类别，不改基础判据

## 二、字段级基准（`[严格]` 口径）

| 指标 | 数值 | 说明 |
|---|---|---|
| 业务字段总数 | 26798 | 全量 54842 − 元数据表 108 − UDF 27936 |
| 标准字段 | 26087 | 并集判据 |
| **非标准字段** | **711** | 对外唯一数字 |
| 真异常字段 | 22 | 含中文 20 + 纯数字 2 |
| 正常变体 | 689 | 7位式 338 + 表别名前缀式 257 + 纯字母 65 + 双侧皆不符 27 + 其他 2 |

### 命名判据（已冻结）

```
形态标准 := ^[A-Z]{2}\d{3}$
实体位:= { table[-2:], table[3:5] }    ← 并集，单侧会误判
```

**为何必须并集**（7 张表两种位置命中数不同，实测）：

| 表 | n | `t[-2:]` | `t[3:5]` |
|---|---|---|---|
| `ACTMS205` | 8 | **0** | **8** |
| `ACTTI205` | 12 | **0** | **12** |
| `DSCINTMA` | 5 | **5** | **0** |
| `WARRANT` | 6 | **6** | **0** |

## 三、表级基准

### 3.1 两个隐藏变量（表级数字反复的真正原因）

元数据有两处易被忽略的口径分歧，**两者叠加产生全部偏差**：

**变量一：表集合基准** —— `fields.json` 与 `tables.json` 是两份表清单，差 5 张

| 集合 | 数量 | 差异 |
|---|---|---|
| `fields`侧 | 1170 | 有字段定义（含4 张孤儿表） |
| `tables`侧 | 1170 | 含元数据表与 PMSTA |

- 仅在 `fields`：`INVLK` `INVLL` `YFMXB` `YSMXB`
- 仅在 `tables`：`PMSTA`（无任何字段）+ 3 张元数据表

**变量二：是否剔除管理字段** —— `MOCTX`/`PURCD`/`PURTC` 的 `CREATOR` 是**业务字段**

| 表 | 列 | 长度 | 中文名 | 是否标准形态 |
|---|---|---|---|---|
| `MOCTX` | `CREATOR` | 7 | `LURUZ` | **否** |
| `PURCD` | `CREATOR` | 7 | `AAAA` | **否** |
| `PURTC` | `CREATOR` | 7 | `录入者` | **否** |

它们长度 7（非标准 `XXnnn` 形态），是真实的命名偏离。
**若把它们当管理字段剔除，这 2 张表的偏离会被掩盖**，全标准/部分非标准的分界就错了。

### 3.2 四种组合的完整实测矩阵

| 表集合 | 管理字段 | 表数 | 全非标准 | 部分非标准 | 全标准 | 含 >=1 非标准 | 勾稽 |
|---|---|---|---|---|---|---|---|
| `fields`侧 | **保留** | 1170 | **27** | **67** | **1076** | **94** | OK |
| `fields`侧 | 剔除 | 1170 | 27 | 65 | 1078 | 92 | OK |
| `tables`侧 | 保留 | 1170 | 25 | 67 | 1077 | 92 | **FAIL** |
| 并集 | 保留 | 1174 | 27 | 67 | 1079 | 94 | **FAIL** |

> 注：`tables`侧与并集的勾稽 FAIL，是因为表集合里包含了**无任何字段的表**
> （`PMSTA`），它们既不能算「全标准」也不算「非标准」，属第四类。

### 3.3 裁决：`[严格]`= fields 侧 1170 + 保留管理字段

| 指标 | 数值 |
|---|---|
| 业务表总数 | **1170** |
| 全部字段均非标准 | **27** |
| 部分非标准 | **67** |
| 全部字段均标准 | **1076** |
| 含 >=1 非标准字段 | **94** |

勾稽：`27 + 67 + 1076 = 1170`　`27 + 67 = 94`

**为什么不用并集 1174**：`PMSTA`（产品文件文档申请单头档）字段为 0，
无法归入三类中的任何一类，强行归入会破坏勾稽。若后续确认该表启用，
再单独说明其归类方式。

**为什么保留管理字段**：`MOCTX`/`PURCD` 的 `CREATOR`（len=7）是真实命名偏离，
剔除会掩盖 2 张表的偏离，且与字段级 `26798` 口径分叉（字段级保留了管理字段）。

### 3.4 历史数字对照（避免再被当成错值）

| 数字 | 出处 | 实际口径 |
|---|---|---|
| 92 / 65 | PM 早期 | tables侧 + **剔除管理字段** |
| 94 / 67 | 架构师、我 | fields侧 + 保留管理字段 |
| `1141` | 架构师 | `[含UDF]` 剔元数据 的**部分非标准表数**（1168 − 27）—— 合法但**无业务含义**（UDF 恒判非标准） |
| 1165 | 我（已修正） | 含 UDF 表数，与 1168 不是修正关系 |
| 1168 / 1171 | 架构师 | 含 UDF 口径 / 并集 |
| 1079 | 脚本中途值（已修正） | 并集口径，勾稽FAIL |

### 3.5 关于 1141（架构师拦下的错误定性）

本规范初稿曾把 1141 标注为「67 的同义写法」，**该定性错误**，经架构师指出后修正。

```
[严格]剔UDF        全非标准27   部分非标准   67   全标准 1076   含>=1   94
[含UDF] 剔元数据      全非标准 27   部分非标准 1141   全标准    2   含>=1 1168
[含UDF] 含元数据      全非标准 27   部分非标准 1144   全标准    2   含>=1 1171
```

| 数字 | 口径 | 性质 |
|---|---|---|
| `67` | `[严格]` | ✅ **唯一有效值** |
| `1141` | `[含UDF]` 剔元数据 | 合法但**无业务含义** —— `UDF01` 不匹配判据恒为非标准，导致 1165 张含 UDF 表全部落入此类 |
| `1144` | `[含UDF]` 含元数据 | 同上（1171 − 27），差 3 为元数据表 |

**两者相差 17 倍，不是同一口径的两种写法。**

记录本条的目的：防止后来者在 `[含UDF]` 口径下拿到 1141 时误判为算错。

## 四、掩码异常基准

### 众数基准法

按 (type_raw, mask) 分组，取组内 precision **众数**为基准；
仅当 type_raw 为 char 且偏离众数时计为异常。

**为何不能用绝对值比对**：MD006(precision) 在不同 MD005 下语义不同 ——

| MD005 | 语义 | 分布 |
|---|---|---|
| char | **字符长度** | 1.0 / 4.0 / 8.0 / 10.0 等 |
| date | 恒为 .0（原生 date 不存长度） | 22/22 全是 .0 |
| numeric | 数值 scale | 16.6 占 84.79% |

用 char 的标尺去量 date，会产生 9 条假异常。

### 众数占比（全部 ≥98%，故众数作基准安全）

| 掩码 | 组内数 | 众数 | 占比 |
|---|---|---|---|
| YMD | 830 | 8.0 | **99.4%** |
| YM | 82 | 6.0 | **98.8%** |
| YMK | 29 | 8.0 | 100% |
| Y | 22 | 4.0 | 100% |
| HHMMSSMMM | 4 | 9.0 | 100% |
| YYYY/MM/DD | 2 | 10.0 | 100% |
| YYMMDDHHMM | 1 | 10.0 | 100% |

**建议断言**：`min(mode_ratio) >= 0.98`。若某掩码众数占比跌破 98%，
说明该掩码语义混用，需人工介入而非自动判异常。

### char 6 条异常（方向是事实，成因是推断）

| 方向 | 数量 | 明细 | 判定（事实） | 成因（推断） |
|---|---|---|---|---|
| **偏小** | 4 | `HRSTC.TC015/TC016`(6 vs 8)<br>`PALNF.NF014/NF015`(6 vs 8) | precision < 众数 | 疑挂错掩码（YMD 8 位装不进 6 位列） |
| **偏大** | 2 | `CMSMA.MA169`(10 vs 6)<br>`ASMTS.TS008`(12 vs 8) | precision > 众数 | 列宽预留过大，掩码未必错 |

> `CMSMA.MA169` 挂 YM **本身是对的**（中文名「固定资产现行年月」正是年月），只是列宽 10 > 6。
> 归入「挂错掩码」会误导开发者去改本正确的掩码。
