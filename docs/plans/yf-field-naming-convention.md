# 易飞数据库字段命名铁律（并集判据，实测 26087 / 26798 = 97.4% 成立）

> 2026-10-08，基于 `ADMMD-字段信息.xml` 的 54842 个字段实测得出。
> **这是易飞与易助最根本的差异之一**，直接影响 SDK 的类型设计与 ER 推断。

---

## 一、核心规律

```
列名 = 表名中的「实体位」 2 位 + 3 位序号
实体位∈ { table[-2:], table[3:5] }      ← 并集，两种位置都可能出现
```

**标准字段判定**（两项须同时满足）：

1. 列名匹配 `^[A-Z]{2}\d{3}$`（长度 5，两字母 + 三位序号）
2. 列名前缀命中表名的**实体位**：`column[:2] == table[-2:]` **或** `column[:2] == table[3:5]`

>  **不可只用单侧。** E10 表名中实体位有两种位置：
>
> | 表名结构 | 例 | 实体位 | 字段前缀 |
> |---|---|---|---|
> | 模块 3 + 实体 2 | `PURTC` | `table[-2:]` = `TC` | `TC001` |
> | 模块 3 + 实体 2 + 版本后缀 | `ACTMS205` | `table[3:5]` = `MS` | `MS001` |
> | 模块 3 + 长实体名 | `DSCINTMA` | `table[-2:]` = `MA` | `MA001` |
>
> 单用 `table[-2:]` 会**漏判 50 条**（`*205` 多层子表实体位在 `t[3:5]`，末 2 位是版本号 `05`）；
> 单用 `table[3:5]` 会**误判 11 条**（`DSCINTMA` / `WARRANT` 实体位在末 2 位，
> 会把 `MA` 读成 `IN`、`NT` 读成 `RA`）。

| 表名 | 字段名示例 | 说明 |
|---|---|---|
| `PURTC`（采购单） | `TC001` `TC002` ... `TC073` | 实体位 `TC` + 序号 |
| `COPTC`（销售单） | `TC001` ... | 同上 |
| `INVMB`（品号） | `MB001` ... `MB287` | 实体位 `MB` |
| `CMSMA`（客户） | `MA001` ... `MA188` | 实体位 `MA` |
| `ACTTA`（会计凭证） | `TA001` ... `TA056` | 实体位 `TA` |
| `ACTMS205`（报表项目类别） | `MS001` ... `MS008` | 版本后缀表，实体位在 `t[3:5]` |

**实测口径**（业务字段 26798 = 全量 54842 − UDF 28008 − 元数据表 3 张共 108 个字段）：

| 判据 | 标准数 | 非标准数 |
|---|---|---|
| 仅按形态（不校验前缀） | 26114 | 684 |
| 严格 `table[-2:]` | 26037 | 761 |
| 严格 `table[3:5]` | 26076 | 722 |
| **并集（本文件采用）** | **26087** | **711** |

非标准 711 条中，**真异常仅 22 条**（含中文列名 20 + 纯数字列名 2），
其余 689 条均属 E10 设计惯例（7 位式 338 / 表别名前缀式 257 / 纯字母 65 / 形态标准但双侧前缀均不符 27 / 其他 2）。

> 口径回归保护：`scripts/gen_data_dictionary.py` 内已加断言，
> 改动判据会直接 assert 失败而非静默产出错误数字。
> 另有 CI 门禁 `npm run check:dictionary`（即 `gen_data_dictionary.py --verify-stats`）：
> **只读** `_gen-stats.json` 并断言冻结计数，不重新生成产物（不会覆盖人工修订的文档）。
> 计数变动会使 CI 直接 FAIL。

## 二、字段名长度分布（5 字符占绝对多数）

| 长度 | 数量 | 说明 |
|---|---|---|
| **5** | **54418** | 标准格式 `XXnnn` |
| 7 | 355 | 长字段名（如 `GHXA018`） |
| 2 | 27 | 无语义 |
| 4 | 13 | 无语义 |
| 其他 | 39 | 少数特殊表 |

**结论：标准字段 = 长度 5 且形态为 `XXnnn` 且前缀命中实体位（`table[-2:]` 或 `table[3:5]`）。**
仅用「首 2 位等于表名末 2 位」会漏判 50 条 `*205` 子表字段；仅用 `table[3:5]` 会误判 11 条。

### 4.2 全部业务字段均非标准的表（27 张）

这些表**没有一条标准字段**，字典生成时须整体按非标准规则标注：

| 形态 | 表数 | 表名 |
|---|---|---|
| 单据性质表（7 位完整表名式） | 17 | `GHXA` `JCXA` `JHXA` `PDXA` `SCXA` `LLXA` `LLJH` `TBXA` `THXA` `TLXA` `WTXA` `WWXA` `XHJH` `XHXA` `XTXA` `YBXA` `ZXXA` |
| 队列表 / 报表格式表（纯字母列名） | 4 | `IWCTRANSQUEUE` `TRANSQUEUE` `RPTGRIDFMT` `RPTGRIDFMTENG` |
| 孤儿表（中文列名，不在 `tables.json`） | 2 | `YFMXB` `YSMXB` |
| 视图 / 混合命名 / 测试表 | 3 | `V_QIXUBING`（`V_` 前缀视图）`EFJOBQUE`（`EF`+`JOBQUE` 混合命名）`DXL`（测试表，创建者 `dingxl`） |
| 字段名退化 | 1 | `PURTG2`（列名仅 `01` `02`，中文名全空） |

表数口径必须区分，否则会差 10 倍以上：

| 口径 | 表数 | 说明 |
|---|---|---|
| 全部业务字段均非标准 | **27** | 真正需特殊处理 |
| 含至少一个非标准字段 | **92** | = 27 全非标准 + 65 部分非标准 |
| （对比）含 UDF 的表 | 1171 | 几乎全库，参考价值低 |

> 上表 92 与 1171 的差异源于**是否计入 UDF**：24 个 UDF 出现在 1171 张表中，
> 只要一张表有 UDF 就必然「含非标准字段」。本节一律采用**剔除 UDF 与管理字段**的
> 严格口径（27 / 92）。

>  早期版本此处写「共 36 张表」，该数字来自只用 `table[-2:]` 的判据，
> 已被第四节 4.1/4.2 的分类取代，**不再使用**。

## 六、格式掩码（MD008）——  2026-10-08 自我纠正

**我最初把 MD008 误判为「代码表关联」**（因取值 `YMD` 像表名）。架构师独立发现并经我复核验证：

**MD008 实为「数据编辑格式掩码」（date/format mask），不是代码表。**

全部 981 个取值：

| 取值 | 字段数 | 性质 |
|---|---|---|
| `YMD` | 841 | 年月日格式符 |
| `YM` | 82 | 年月格式符 |
| `YMK` | 29 | 年月+格式变体 |
| `Y` | 22 | 年格式符 |
| `HHMMSSMMM` | 4 | 时分秒毫秒格式符 |
| `YYYY/MM/DD` | 2 | 日期格式符 |
| `YYMMDDHHMM` | 1 | 日期时间格式符 |

**没有一个是代码表名。**

### 二次纠正（2026-10-08 PM 实测复核）：三个长掩码**不是**录入错误

我最初把 `HHMMSSMMM` / `YYYY/MM/DD` / `YYMMDDHHMM` 判为「数据录入错误」，**该判断错误，已撤回**。

实测：**掩码位数 == precision**，是合法的显式掩码。

| 掩码 | 位数 | precision | 相等 | 样例 |
|---|---|---|---|---|
| `HHMMSSMMM` | 9 | 9.0 | 是 | `INVLA.LA022` 审核时间 |
| `YYYY/MM/DD` | 10 | 10.0 | 是 | `EISLI.LI010` 账款截止日期 |
| `YYMMDDHHMM` | 10 | 10.0 | 是 | `GFCME.ME003` LOG作业时间 |

**更强证据**：`MD007`（`column_cn2`）字段中有 **979 行直接标注掩码语义**，格式为：

```
交易日期[FORMATE:YMD]
年月[FORMATE:YM]
单据日期[FORMATE:YMD]
```

这是易飞官方在元数据中明示的格式掩码，**证据等级高于任何外部推断**。

**判据更新（完整版，按证据强度排序）**：

1. `MD007` 含 `[FORMATE:xxx]` → 官方明示，**最高置信**
2. `char` 类型 + 日期掩码 + 位数与 precision 一致 → 确认掩码
3. `date` 类型 + 掩码 → 冗余（同族支持）
4. `numeric` + 掩码 → 异常使用（仅 2 处，落在测试表）

###  三次纠正（2026-10-08 team-lead 裁决）：17 个 → **6 个**，改用众数基准法

上一版按「掩码位数 == precision **绝对值**」判定异常，得17 个，**该基准是错的**。

**根因**：`MD006`（precision）在不同 `MD005` 下语义完全不同：

| MD005 | MD006 实际语义 | 能否与掩码位宽比对 |
|---|---|---|
| `C` char | 字符长度 | 能 |
| `D` date | 数值精度 scale，**恒为 `.0`**（实测 22/22 条） | 不能 |
| `N` numeric | 数值精度 scale，如 `16.6` | 不能 |

用绝对值比对，等于把 `D` 类型的 `.0` 当成「长度缺失」，凭空造出 **9 条假异常**
（`EISL` 族 8 条 + `SASLA.LA015` 1 条，均为挂 `YMD` 的 date/numeric 字段）。

**众数基准法**：按 `(type_raw, mask)` 分组，取组内 `precision` **众数**为基准，
仅当 `type_raw =='C'` 且偏离众数时才计为真异常。

| 类型 | 掩码 | 组内数 | 众数 | 占比 | 偏离 |
|---|---|---|---|---|---|
| `C` | `YMD` | 830 | `8.0` | 99.4% | 5 |
| `C` | `YM` | 82 | `6.0` | 98.8% | 1 |
| `C` | `YMK` | 29 | `8.0` | 100% | 0 |
| `C` | `Y` | 22 | `4.0` | 100% | 0 |
| `C` | `HHMMSSMMM` | 4 | `9.0` | 100% | 0 |
| `C` | `YYYY/MM/DD` | 2 | `10.0` | 100% | 0 |
| `C` | `YYMMDDHHMM` | 1 | `10.0` | 100% | 0 |
| `D` | `YMD` | 9 | `.0` | 100% | 0（不适用校验） |
| `N` | `YMD` | 2 | `1.0` | 100% | 0（不适用校验） |

**真异常 6 个**（全为 `C` 类型）：

按**偏离方向**分类（不使用中文名关键词，避免误判）：

| 表 | 列 | 中文名 | 掩码 | 众数 | 实际 | 方向 | 性质 |
|---|---|---|---|---|---|---|---|
| `HRSTC` | `TC015` | 工作年月起 | `YMD` | `8.0` | `6.0` | 偏小 | **疑挂错掩码**（装不下 8 位，应 `YM`） |
| `HRSTC` | `TC016` | 工作年月迄 | `YMD` | `8.0` | `6.0` | 偏小 | 同上 |
| `PALNF` | `NF014` | 服务年月起 | `YMD` | `8.0` | `6.0` | 偏小 | 同上 |
| `PALNF` | `NF015` | 服务年月迄 | `YMD` | `8.0` | `6.0` | 偏小 | 同上 |
| `CMSMA` | `MA169` | 固定资产现行年月 | `YM` | `6.0` | `10.0` | 偏大 | 掩码本身正确，仅列宽预留过大 |
| `ASMTS` | `TS008` | 处理日期 | `YMD` | `8.0` | `12.0` | 偏大 | 同上 |

- **长度偏小 4 条**：`YMD`(8 位) 挂在 6 位列上，装不下，最可能是挂错掩码（应为 `YM`）
- **长度偏大 2 条**：掩码与中文名语义一致，只是列宽大于掩码位数，属另一种成因

> 判定依据是**偏离方向**而非中文名是否含「年月」——
> `CMSMA.MA169` 中文名含「年月」但挂的是正确的 `YM`，若按关键词归类会被误判为「挂错掩码」。
> 「方向」是事实，「成因」是推断，二者须分开表述。
`YFMXB.出入` / `YSMXB.出入` 不再计入异常（属孤儿表架构异常，单列）。

> 方法论教训：**同一标尺不能量两种语义**。判定异常前须先确认「这个字段在该类型下
> 到底表示什么」，而非直接套用「值应等于某个绝对数」的直觉。


### 二次纠正（2026-10-08 PM 实测复核）：三个长掩码**不是**录入错误

我最初把 `HHMMSSMMM` / `YYYY/MM/DD` / `YYMMDDHHMM` 判为「数据录入错误」，**该判断错误，已撤回**。

实测：**掩码位数 == precision**，是合法的显式掩码。

| 掩码 | 位数 | precision | 相等 | 样例 |
|---|---|---|---|---|
| `HHMMSSMMM` | 9 | 9.0 | 是 | `INVLA.LA022` 审核时间 |
| `YYYY/MM/DD` | 10 | 10.0 | 是 | `EISLI.LI010` 账款截止日期 |
| `YYMMDDHHMM` | 10 | 10.0 | 是 | `GFCME.ME003` LOG作业时间 |

### 关键含义

1. **易飞元数据不含枚举码值表** —— 字段的枚举定义（如 `approve_status = Y.已审核`）不在 `ADMMD` 里。
   枚举翻译仍需 T-07（真机采集），但这是**数据缺口**，不是「查表能力」问题。

2. **SDK 必须支持格式掩码解析** —— 841 个字段带 `YMD`，说明易飞大量字段是日期型。
   `CREATE_DATE`（长度 17，值如 `20250305181000333`）正是此类。

3. **`code_table` 列名是契约误命名** —— 架构师已在 `fields.json` 中同时保留
   `code_table`（契约列名）与 `format_mask`（真实语义）。**下游一律以 `format_mask` 为准**。

### 枚举值的真实来源

| 来源 | 可得性 |
|---|---|
| `ADMMD-字段信息.xml` |  只有字段定义，无枚举值 |
| 易飞规格文档 / 字典表 | 待收集 |
| 真机采集（query 取实际取值去重） | 可行，T-07 |

## 七、对 SDK 设计的影响

### 7.1 类型定义不能假设语义字段名

由于字段名是 `XX001` 这类无语义编码，**SDK 的领域模型必须依赖中文名映射**：

```typescript
// 不可行：字段名无语义
interface PurchaseOrder { TC001?: string; TC002?: string; }  // 含义不明

// 可行：查字典得中文名，映射为语义字段
interface PurchaseOrder {
  docTypeNo: string;   // 单别 TC001
  docNo: string;       // 单号 TC004
  supplierNo: string;  // 供应商编号 TC005
}
```

**因此 `knowledge/data-dictionary/field-index.csv` 是 SDK 类型生成的必要输入**，
SDK 需要一个「中文名 → 语义字段名」的映射工具。

### 7.2 格式掩码解析是刚需（比枚举更紧迫）

由于 `YMD` 格式掩码关联了 841 个字段，SDK 必须能按掩码解析日期值。
`field-index.csv` 需要暴露 `format_mask` 列，SDK 提供 `parseByMask(value, mask)`。

### 7.3 枚举码值表缺失（数据缺口，非能力缺口）

易飞元数据**不含枚举定义**。`approve_status = Y.已审核` 的映射关系
既不在 `ADMMD` 也不在 `ADMMC`，只能靠真机采集（T-07）。
SDK 的 `EnumValue` 类型仍需保留（承载编码 + 中文 + 翻译状态），
但翻译数据要等 T-07。

### 7.3 ER 推断的正确做法

之前我按 `_no` 后缀做ER 推断 —— **易飞根本不用 `_no` 命名**，规则全错。
正确的推断依据是：

| 置信度 | 依据 | 说明 |
|---|---|---|
| **高** | 实体位相同 + 中文名同义 | 如 `PURTC`(采购单) 与 `PURTD`(采购明细) 共享 `TC001`/`TD001` 的对应语义（实体位取并集口径） |
| **中** | 中文名完全一致 + 同模块 | 如「客户编号」在多张表中同名 |
| **低** | 仅同模块 | 需人工确认 |

单头/单身配对则依赖已验证的 175 个 `node_name`
（如 `purchase_order_data` ↔ `purchase_order_detail_data`）。

## 八、与易助的对比

| 维度 | 易飞（E10） | 易助 |
|---|---|---|
| 字段命名 | `XX001` 编码制（并集判据，非单一「末 2 位」） | 语义化命名（如 `doc_no` `customer_no`） |
| 可读性 | 极低，须查字典 | 高，可直接理解 |
| 字典依赖 | **强依赖**（无字典无法理解字段） | 弱依赖 |
| 枚举查表 | 强需求（YMD 关联 841 字段） | 弱需求 |
| OpenAPI 节点名 | 逻辑节点名（`*_data`） | 数组式 `groups` |

**这个差异比此前识别的一切差异都更根本** —— 它意味着
**易飞 SDK 必须内置字典查询层**，而非像易助那样可以直接映射语义字段。
