## 一、43 个 MA012 未注册节点

### 1.1 问题描述

T-17 批量实测 175 个 `*_data` 逻辑节点名时，43 个节点返回 `OAPMA.MA012未定義` `[口径：runs/node-name-verify.json 归一统计]`。这意味着这些节点未在 OAPMA 注册表中登记，**不是 node_name 写法错误**（AD-12 已确认逻辑节点名即正确用法），而是易飞服务端尚未为这些对象开通单身查询能力。

### 1.2 影响范围

| 项 | 内容 |
|---|---|
| **阻塞阶段** | Phase 2（CRUD 单身查询功能不完整） |
| **影响对象数** | 43/175 个单身节点 `[口径：node-name-verify.json]` |
| **业务影响** | 这 43 个对象的单身字段无法通过 OpenAPI 查询，只能查单头 |

### 1.3 问询内容

> **致：易飞 OpenAPI 服务端团队**
>
> 以下 43 个 `*_data` 节点在真机调用时返回 `OAPMA.MA012未定義`，请确认：
> 1. 这些节点是否计划注册到 OAPMA？预计时间表？
> 2. 若不计划注册，是否有替代方案获取这些对象的单身数据？
> 3. 是否存在「需额外授权/配置才能启用」的情况？
>
> 完整节点清单见附件 `runs/node-name-verify.json` 中 `status=MA012` 的条目。

### 1.4 降级方案

| 降级路径 | 可行性 | 代价 |
|---|---|---|
| A. 仅查单头，跳过单身 | ✅ 可行 | 43 个对象的单身数据不可用，助手功能受限 |
| B. 走数据库直连补全 | ⚠️ 有条件 | 需 P4 视图覆盖这些对象；Analysis 层可绕过 OpenAPI |
| C. 等待易飞端注册 | ⏸ 被动 | 时间不可控 |

**推荐策略**：Phase 1~2 采用 A+B 组合——CRUD 层接受限制，Analysis 层通过视图补全。Phase 3+ 视易飞端响应决定是否切换。

### 1.5 问询状态

> **✅ 2026-10-09 已自行解决，无需发送。** 降级方案 A（仅查单头跳过单身）已确认可行，不阻塞 MVP。OAPMA 集成验证已补充 6 个服务名（typekey_map 595→601）。剩余 43 个 MA012 节点为易飞端未注册，我方无法解决但已有降级路径。

| 项 | 状态 |
|---|---|
| 问询函起草 | ✅ 已完成（本文 §1.3） |
| 发送 | ✅ 无需发送（降级方案已确认可行） |
| 对方回复 | — 不需要 |
| 降级方案确认 | ✅ 已确认（A：仅查单头 + B：Analysis 视图补全） |

## 二、22 个 yf.ai.* 端点清单

### 2.1 问题描述

易助侧已有 22 个 `yz.ai.*` 分析助手端点上线运行。易飞侧目前仅在 `rbac.ts` 中硬编码了 2 个端点（`yf.ai.PurchaseBusinessWarning` / `yf.ai.SalesbusinessWarning`），其余 20 个端点的 service 名、入参、出参均未提供 `[口径：代码搜索 yf.ai. 匹配数]`。

### 2.2 影响范围

| 项 | 内容 |
|---|---|
| **阻塞阶段** | Phase 2（分析助手无法直调服务端，需走降级路径） |
| **影响助手数** | 20/22 个分析助手 `[口径：22 总数 - 2 已确认]` |
| **业务影响** | 分析助手无法利用服务端预计算能力，需本地重建计算逻辑 |

### 2.3 问询内容

> **致：易飞 AI 服务端团队**
>
> 易助侧已有 22 个 `yz.ai.*` 分析助手端点。易飞侧目前仅确认 2 个（PurchaseBusinessWarning / SalesbusinessWarning）。请提供：
> 1. 易飞侧完整的 `yf.ai.*` 端点清单（service 名 + 入参 + 出参定义）
> 2. 这些端点是易飞服务端原生实现，还是易助兼容层转发？
> 3. 若部分端点暂不可用，请标注可用状态与预计时间表
>
> 参考：易助侧 22 个助手清单见 YZCLI `skills/yzcli-erp/references/assistants/` 目录。

### 2.4 降级方案

| 降级路径 | 可行性 | 代价 |
|---|---|---|
| A. query.get 取数 + experts 引擎本地计算 | ✅ 可行 | 性能低于服务端预计算；需从零实现 20 个计算公式 |
| B. 仅做 3 个冒烟助手，推迟其余 19 个 | ✅ 可行 | MVP 范围缩小，但可按期交付 |
| C. 等待易飞服务端提供 | ⏸ 被动 | 时间不可控 |

**推荐策略**：MVP 采用 B——只做 3 个冒烟助手（工厂查询 / 工厂读取 / 客户新增），不依赖 `yf.ai.*` 端点。Phase 3+ 视端点清单到位情况逐步扩展。

**降级路径详细流程**（当端点清单最终到位前的过渡方案）：

```
用户提问 → 智能问数路由 → 识别所需数据
    │
    ├─ 有对应 yf.ai.* 端点 → 直调服务端（最优）
    │
    └─ 无对应端点 → query.get 取原始数据
         → yfcli-experts 引擎本地计算
         → 生成带口径标签的报告
```

## 四、5 个未知业务主键

### 4.1 问题描述

`typekey_map.yaml` 中有 5 个对象标记为 `primary_key_unknown: true` `[口径：grep primary_key_unknown 计数]`。其中第 5 个 `item.inventory.qty` 在真机探测时导致服务端 DLL 崩溃（HTTP 500 + HTML 响应），其余 4 个尚未探测。

### 4.2 影响范围

| 项 | 内容 |
|---|---|
| **阻塞阶段** | Phase 1（CRUD read/update/delete 需要主键定位） |
| **影响对象数** | 5/106 个业务对象 `[口径：typekey_map.yaml primary_key_unknown 计数]` |
| **业务影响** | 这 5 个对象无法执行按主键的 read/update/delete 操作 |
| **特殊风险** | `item.inventory.qty` 探测会导致服务端 DLL 崩溃，**禁止在生产环境重试** |

### 4.3 问询内容

> **致：易飞 OpenAPI 服务端团队**
>
> 以下 5 个对象的业务主键无法从 Apipost 文档自动抽取，请提供：
> 1. [对象1] → 业务主键字段名？
> 2. [对象2] → ...
> 3. [对象3] → ...
> 4. [对象4] → ...
> 5. `item.inventory.qty` → 业务主键字段名？⚠️ 注意：此前尝试以 `item_no` 为主键调用 read 接口，导致服务端 DLL 崩溃（HTTP 500）。请在测试环境验证后再回复。
>
> 完整对象清单见 `knowledge/typekey/typekey_map.yaml` 中 `primary_key_unknown: true` 的条目。

### 4.4 降级方案

| 降级路径 | 可行性 | 代价 |
|---|---|---|
| A. 真机探测（排除 item.inventory.qty） | ⚠️ 部分可行 | 4 个对象可探测；第 5 个有 DLL 崩溃风险 |
| B. 从 data-dictionary SDD 文件推断 | ⚠️ 有条件 | SDD 中的 PK 标记不一定与 OpenAPI 主键一致 |
| C. 等待易飞服务端确认 | ⏸ 被动 | 时间不可控 |
| D. 跳过这 5 个对象的写操作 | ✅ 可行 | MVP 范围缩小 |

**推荐策略**：Phase 1 先对 4 个安全对象执行 A+B 交叉验证；`item.inventory.qty` 单独标记为「高危」，仅在测试环境由易飞方协助探测。MVP 可接受 D 作为兜底。

### 4.5 问询状态

> **✅ 2026-10-09 已关闭。** 原 5 个未知主键中 4 个已通过真机反推解决（company.detail→company_no / employee→staff_no / operation→routing_no / document.type.general→doc_type_no）。剩余 item.inventory.qty 和 subscription 为只读查询对象，无业务主键，仅支持 query，已在 typekey_map.yaml 中标注 primary_key_note 并移除 primary_key_unknown 标记。无需易飞回复。
