### 核心结论：协议 90% 同源，差异在实现质量与工程加固

**同构部分（可直接复用）**：`digi-service` / `digi-user-token` / `Content-Type` 三头同名；`std_data`→`parameter` 封包同；`execution.code` 判据同；`result.success`/`result.error` 双通道同；8 种操作（易飞多 `invalid` 作废）；分页语义同（`page_no` 从1起 / `page_size` 最大 10000 / `use_has_next`）；`conditions` 运算符集同；排序 `orders` 同；权限三维度同。

**5 个高风险差异**：
1. **`conditions` 结构完全不同**（最危险）：易飞是**对象** `{operator, fields[]}` + 组用 `fields[].group` 嵌套；易助是**数组** `[{groups:[...], groups_operator}]`。结构不匹配时**不报错、静默返回全量**。必须写双向转换层 + 专项测试闸门。
2. **易飞无 `fastquery`**：易助有 `query`(调TPAOpenAPIProcess.exe) + `fastquery`(SQL缓存直查) 双通道，且 SKILL.md 明确「只用 fastquery」；易飞仅 `query.get` 一个，**每次重查数据库**。易助性能优化经验在易飞侧失效。
3. **易飞无任何 AI 私有端点**：文档中 0 个 `yf.ai.*`（易助有 8 个 `yz.ai.*` + 2 个 `yf.ai.*`）。→ 易助 22 个分析助手（02~17）不能复刻，须改走「query.get 取数 → erp-experts 引擎计算 → 本地生成报告」。
4. **易飞无 TypeKeyList / help 服务**：只能从 48MB JSON 静态抽取生成 `typekey_map.yaml`。
5. **易飞 Token 获取方式文档未说明**（易助明确「通过 ERP 作业 设置授权人员 TPASC19 获取」）→ **Phase 0 最高优先级阻塞项（编号 B1）**。

### 与易助格式的对齐决策
易助表头是 `| 字段编号 | 名称 | 节点名称(别名) | 类型 | 备注 |`，但**易飞不存在字段编号体系**（那是易助 DLL 专有）。易飞是「节点名（小写，API 收发参实际用）↔ 字段名（大写，DB 物理列名）」双轨，故输出 5 列：

### 探查发现的 5 个陷阱（全部已在脚本注释中记录）

**① `not_null` 无区分度**：全库 21,206 个标记为 1、50 个为 -1，**所有字段都是 not_null=1**，含只读字段与管理字段。→ 不可作必填判据。改用「字段是否出现在 create/update 入参」这一客观事实判定可写性。

**② `create` 只列必填，`update` 才是完整字段集**：sales.order create仅 8 个字段，update 有 53 个。→ 必须 create ∪ update 取并集，否则漏采绝大多数字段。实现时用 `sources: Set<op>` 记录字段来源，据此输出必填/可选/可写三态。

**③ 同一服务名有多个重复节点，多数 `raw_parameter` 为空**：`yf.oapi.purchase.invoice.data.create` 有 10 个节点，9 个为空只有 1 个有 17 条。→ 合并时必须「**非空优先**」，空节点绝不覆盖有内容的节点。此bug 修复后字段数 2,805 → 3,065 →（补响应侧）12,893。

**④ 响应侧是纯只读对象的唯一字段来源**：28 个对象无 create/update，原本字段全空。改为从 `query` 的 `parameter.result.rows.*` 与 `read` 的 `parameter.result.success.*` 抽取，并标记 `readOnlyFields`（仅见于回参 → 疑似系统生成）。

**⑤ 节点名跨层需归一**：三层嵌套时 key 为 `ap_refund_doc_data.ap_refund_doc_detail_data`，但 `node_name` 查询条件用的是**裸单身节点名** `ap_refund_doc_detail_data`；响应侧路径还多一层 `parameter.result.success.` 前缀。→ 统一取末段。

### 发现易飞官方文档 bug（5 个对象）
`yf.oapi.ap.refund.doc.data.create`（**应付退款单**）的入参容器写作 `wo_stockin_data`（**生产入库单**）—— 复制粘贴错误。脚本加了启发式检测（容器名与对象名无共同词则标注），命中 5 个对象：`ap.refund.doc` / `op.stockin` / `prepayment.doc` / `transfer` / `wo.commence`。已在对应 md 中以「⚠️ 文档异常（官方 Apipost 文档问题，非抽取缺陷）」显式标注。

### CI 门禁（--check）设计教训
初版只比对 `_index.json` → **篡改单个 md 检测不到**（门禁漏洞）。改为全量指纹（FNV-1a32）覆盖索引 + 106 个 md，四种场景已验：正常 PASS / 篡改单文件 FAIL / 删除文件 FAIL / 恢复 PASS。指纹须过滤 `generated_at` 行（正则 `/^\s*#?\s*generated_at:/`，**初版漏了 `#` 前缀的注释行导致假失败**）。

### 行尾归一化教训
初版脚本用「有变化才转换」判断，校验却报 108 个异常 —— 逻辑不自洽。改为**幂等归一化**（先全去 CRLF 再统一加），111 个文件一次通过 0 异常。
